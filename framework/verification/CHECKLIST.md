# 변경 검증 체크리스트

변경 기록 또는 PR에서 필요한 항목만 사용한다. 체크는 실제 증거가 있을 때만 한다. N/A는 사유, 미실행은 필요한 환경/조건을 적는다.

## 공통

- [ ] 목적·수용 기준·비범위를 확인했다.
- [ ] 관련 지침·계약·소비자·기존 테스트·사용자 변경을 확인했다.
- [ ] 위험도와 PATCH/REBUILD 선택 이유가 타당하다.
- [ ] 모듈 내부 import와 타 모듈 데이터 쓰기 위반을 점검했다.
- [ ] 필요한 실제 검사 또는 직접 확인을 수행했다.
- [ ] 검증 실패를 없애려고 기대값/게이트를 약화하지 않았다.
- [ ] diff와 비밀값·민감 로그를 점검했다.
- [ ] 행동 변경에 맞게 계약/문서를 갱신했다.
- [ ] 통과·실패·미실행·잔여 위험을 정확히 기록했다.

## 공개 행동·업무 변경

- [ ] 요구사항에서 성공·실패·경계 정답을 도출했다.
- [ ] 소비자·오류·부작용·권한·호환성을 확인했다.
- [ ] 필요한 회귀·계약·통합 검증을 수행했다.
- [ ] 권한/테넌트/멱등성/동시성 영향에 맞는 검사 결과가 있다.

## 영속 데이터 변경

- [ ] 대상 환경과 데이터 소유자·쓰기 권한을 확인했다.
- [ ] 구/신 코드·스키마 호환성과 배포 순서를 검증했다.
- [ ] 잠금·부하·재개·불변조건을 격리 DB에서 확인했다.
- [ ] 코드 복구와 데이터/부작용 복구를 구분했다.
- [ ] 필요한 백업·복원 검증과 적용 허가가 준비돼 있다.

## REBUILD

- [ ] 교체 경계·기준점·계약·검증·복구 조건이 갖춰졌다.
- [ ] 같은 계약 시나리오를 구/신 구현에 적용했다.
- [ ] 기존 데이터·소비자·성능·부작용 호환성을 확인했다.
- [ ] 관찰된 차이는 버그/허용 차이/회귀로 분류했다.
- [ ] shadow 실행이 부작용을 중복 실행하지 않는다(또는 N/A).
- [ ] 전환·중단·복구 조건과 안정화 후 정리 계획이 있다.

## 증거

| 항목 | 실행/확인 방법 | 결과 | 환경/기준점 | 미실행 또는 N/A 사유 |
|---|---|---|---|---|
| <항목> | <값> | <값> | <비밀 제외> | <값> |

미충족 항목이 적용에 필수라면 구현 상태와 적용 준비 상태를 분리해 보고한다.
