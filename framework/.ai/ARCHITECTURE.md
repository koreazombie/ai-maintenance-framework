# 아키텍처 규칙

## 기본 형태

비즈니스 기능별 모듈러 모놀리스 + 필요한 경계의 포트/어댑터 + 행동 계약을 출발점으로 삼는다. 독립 배포·확장·장애 격리 필요가 입증되기 전에는 마이크로서비스로 분리하지 않는다.

```text
src/modules/<business-module>/
  public/          공개 입력·출력·포트·이벤트 계약
  domain/          불변조건과 상태 전이
  application/     유스케이스와 포트 호출
  infrastructure/  DB·외부 API·메시지 어댑터
  README.md        책임·데이터·계약·검증 경로
src/composition/   어댑터 조립과 트랜잭션 조정
contracts/         모듈별 행동 명세
```

이 디렉터리는 추천형이다. 작은 모듈에는 파일 몇 개로 충분하며 기존 구조와 언어 관례에 맞게 매핑한다.

## 의존성 방향

- 도메인은 웹 프레임워크·DB·외부 SDK를 직접 의존하지 않는다.
- 애플리케이션은 도메인과 필요한 포트를 사용한다. 어댑터는 포트를 구현한다.
- 조립부는 구현을 알고 연결할 수 있다. 모듈 소비자는 공개 진입점을 사용한다.
- 공개 타입에서 ORM 엔티티·DB 클라이언트·내부 클래스가 새어 나오지 않게 한다.
- 다른 모듈의 리포지토리·서비스 내부·테이블 쓰기 경로를 직접 사용하지 않는다.
- 순환 의존을 발견하면 책임 이동·명시적 조정자·이벤트를 검토한다. 무조건 이벤트로 바꾸지 않는다.

## 일관성부터 정하기

호출 방식 전에 불변조건을 정한다. 예약 저장과 회원권 차감이 원자적이어야 한다면 모놀리스에서는 조정자가 하나의 트랜잭션 안에서 소유 모듈의 공개 작업을 호출하도록 설계할 수 있다. 모듈 계약은 중립적인 작업 범위 포트를 쓰고 실제 DB 핸들은 인프라에 둔다.

서로 다른 DB·프로세스를 쓰면 로컬 트랜잭션만으로 원자성을 보장할 수 없다. 허용 가능한 지연, 보상, 재시도, 장애 상태를 계약에 명시한다. DB 기록과 이벤트 발행을 묶어야 하면 transactional outbox와 소비자 멱등성을 검토한다.

## 공통 코드 기준

명확하게 같은 의미와 변경 이유를 가진 코드만 공유한다. 날짜·ID·오류 구조 같은 작고 안정적인 기술 요소부터 공유한다. 예약·결제 업무 규칙을 `shared/utils`로 옮겨 경계를 숨기지 않는다. 단순 반복을 없애기 위해 서로 다른 업무를 하나의 거대 서비스로 결합하지 않는다.

중요한 선택은 `templates/ADR.md`에 이유·대안·되돌릴 조건을 남긴다. 목표는 설계 설명의 양이 아니라, 다음 작업자가 결정 근거를 확인할 수 있는 정도다.
