# AI 작업 프로세스

## 읽기와 범위 설정

1. 요청의 목적·수용 기준·비범위를 파악한다.
2. 실제 저장소 구조, 프로젝트 설정, 적용 지침, 미커밋 변경을 확인한다.
3. 관련 모듈·공개 계약·데이터·소비자·기존 검증을 읽는다.
4. 위험도와 PATCH/REBUILD를 정한다. 읽지 않은 파일을 이해했다고 주장하지 않는다.

필수 정보가 부족하면 중요한 질문만 묻고 독립적인 조사·준비는 계속한다. 안전한 로컬 작업과 확인이 필요한 적용을 구분한다.

## 계획과 구현

- 낮은 위험: 짧은 설명으로 바로 수정한다. 별도 변경 문서·ADR을 강제하지 않는다.
- 보통 위험: 수용 기준·영향·검증 계획을 먼저 정리한다. 지속 기록은 필요할 때 `.ai/templates/CHANGE.md`를 사용한다.
- 높은 위험: 변경 기록과 적용·복구 계획을 파일로 남긴다. REBUILD는 준비 조건을 확인한다.

기존 API·계약·명령을 우선 재사용한다. 필요한 새 의존성은 실제 필요·대안·비용을 설명하고 프로젝트 정책을 따른다. 추측성 범위 확장과 무관한 포맷 변경을 피한다.

## 검증과 인계

1. 변경에 맞는 검사와 실행 가능한 회귀 검증을 수행한다.
2. 실패 원인을 조사해 수정한다. 기대값과 게이트를 약화해서 통과시키지 않는다.
3. diff에서 내부 의존·타 모듈 데이터 쓰기·권한 누락·원하지 않은 파일 변경을 확인한다.
4. 행동이 바뀌면 계약·모듈 설명·프로젝트 설정을 함께 갱신한다.
5. 결과, 변경 이유, 실제 검증, 미실행 항목, 위험과 다음 적용 조건을 보고한다.

프로젝트의 완료 기준과 필요한 검사가 충족될 때까지 허가된 작업을 이어간다. 환경 문제로 검사가 막히면 결과를 보존하고 정확한 상태와 해결에 필요한 정보를 알린다.

## 긴 작업과 다음 AI를 위한 기록

고위험 또는 여러 세션 작업은 `.ai/changes/` 같은 프로젝트 지정 경로에 목표, 기준점, 읽은 계약, 결정, 완료/남은 작업, 검증과 복구 경로를 남긴다. 비밀값이나 긴 대화 원문은 저장하지 않는다. 다음 AI는 기록을 읽은 뒤 현재 코드와 환경을 다시 확인한다.

최종 보고의 권장 형식은 '무엇을/왜 변경했는지 → 어떤 검사에서 무엇을 확인했는지 → 남은 제약 또는 적용 조건'이다. 실행하지 않은 검사는 통과로 표시하지 않는다.

## 설치 상태 검사

지침·설정 변경 후 `.ai/tools/validate_installation.py`를 실행한다. 의도적인 사용자 설정/병합 진입점 변경만 검토한 뒤 원본 저장소의 scripts/record_installation.py --refresh로 기준을 갱신한다. 실패를 숨기려고 기준을 갱신하지 않는다. 짧은 테스트/CI 요청도 기존 검사 조사 → 필요한 검사 구현·로컬 실행 → CI 연결 → 실제 실행·필수 병합 조건 확인 순서로 처리하며 권한 부족과 미실행을 구분한다.
