# 모듈 경계와 크기

## 경계를 정하는 다섯 질문

| 기준 | 질문 | 근거 |
|---|---|---|
| 업무 책임 | 한 문장으로 책임을 설명할 수 있는가? | 유스케이스·불변조건 |
| 변경 독립성 | 어떤 이유로 함께 바뀌는가? | 변경 이력·요구사항 |
| 데이터 소유권 | 데이터 쓰기와 정합성을 누가 책임지는가? | 테이블·이벤트 소유자 |
| 계약 안정성 | 외부에 필요한 최소 행동은 무엇인가? | 소비자와 공개 계약 |
| 재생성 가능성 | 내부를 교체해도 소비자와 데이터가 유지되는가? | 계약 테스트·복구 경로 |

모듈은 한 업무 개념, 명시적 공개 진입점, 데이터 소유자, 독립적인 검증 방법을 가져야 한다. 코드 줄 수나 AI의 컨텍스트 크기를 절대적인 분리 기준으로 쓰지 않는다. 관련 파일이 여러 모듈에 흩어지고 매번 함께 수정된다면 경계를 재검토한다.

## 소유권

- 쓰기 소유자는 데이터별 하나를 기본으로 한다. 다른 모듈은 공개 작업·조회 계약·이벤트를 사용한다.
- 같은 PostgreSQL을 써도 소유권은 나눌 수 있다. DB를 반드시 모듈마다 분리할 필요는 없다.
- 직접 조회·교차 조인·분석 뷰가 필요한 경우 소유자, 읽기 전용 범위, 스키마 변경 영향과 테스트를 기록한다. 분석 예외로 업무 쓰기를 허용하지 않는다.
- 외래 키는 무결성을 돕지만 스키마 결합도 만든다. 유지/제거 판단 근거와 마이그레이션 순서를 적는다.
- 순환 호출, 범용 관리자 서비스, 모든 모듈이 수정하는 테이블은 경계 문제의 신호다.

## 과도한 분할 방지

검증기·매퍼·팩토리를 무조건 독립 모듈로 만들지 않는다. 하나의 불변조건을 설명하기 위해 많은 파일을 오가면 응집도를 높인다. 독립적인 업무 규칙이나 교체 가능한 외부 연결이 없다면 인터페이스도 필수가 아니다.

## 레거시 적용

위반을 발견해도 요청과 무관한 전체 개편을 하지 않는다. 현황·예외·위험을 기록하고, 변경 대상부터 공개 경로와 테스트를 만든다. 기존 예외는 경로·소유자·사유·검증·해소 조건을 `.ai/PROJECT.md`에 기록한다. 신규 위반을 기존 예외에 묻어 넣지 않는다.
