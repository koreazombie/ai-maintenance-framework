# 데이터 보호

모듈 REBUILD는 구현 교체다. 데이터 삭제·초기화·스키마 재작성 권한을 의미하지 않는다. 영속 데이터, 파일 저장소, 큐, 캐시의 장기 상태까지 영향 범위를 조사한다.

## 환경과 권한

명령 실행 전에 대상 환경·호스트·DB·역할을 비밀값을 노출하지 않는 방법으로 확인한다. 환경이 미확인인 DB에 쓰기·리셋·마이그레이션 명령을 실행하지 않는다. 테스트는 명시적으로 분리된 일회용 DB를 사용한다. 이름에 `test`가 있다는 이유만으로 안전하다고 판단하지 않는다.

운영 DROP/TRUNCATE/전체 DELETE, 파괴적 마이그레이션, 복원은 구체적 대상·범위·복구 절차에 대한 허가를 확인한다. 기존 명시적 허가 범위 안에서는 반복 승인 요구를 하지 않는다. 일반 기능 개발 허가는 운영 데이터 변경 허가로 해석하지 않는다.

## 마이그레이션 원칙

- 이미 배포된 마이그레이션을 수정하지 않고 새 마이그레이션을 만든다.
- 가능하면 expand → backfill → 소비자 전환 → 관찰 → contract 순서로 수행한다.
- 추가 컬럼·병행 읽기/쓰기 기간과 구/신 코드 호환성을 확인한다.
- backfill은 작은 배치, 재개 위치, 중복 실행 안전성, 검증 쿼리를 갖춘다.
- FK·UNIQUE·NOT NULL과 잠금 시간·테이블 크기·타임아웃을 검토한다.
- 적용 전후 행 수만 비교하지 않는다. 키·합계·참조·불변조건도 확인한다.
- 백업 존재와 복원 가능성을 구분한다. 운영 영향이 크면 격리 환경의 복원 검증과 허용 복구 시간·손실 범위를 기록한다.

## 코드 복구와 데이터 복구는 다르다

코드 롤백으로 이미 저장된 데이터·발송 메시지·결제·외부 부작용을 되돌릴 수 없다. 새 스키마와 구 코드의 호환 기간을 확보하고, 쓰기 중단·forward fix·보상·백업 복원 중 가능한 방식을 정한다. 복원은 복원 시점 이후의 정상 쓰기를 잃을 수 있으므로 별도 판단이 필요하다. 자동 down migration을 기본 복구책으로 삼지 않는다.

## 비밀과 개인정보

실제 토큰·비밀번호·DB 접속문자열·고객 데이터는 계약, 테스트 fixture, 프롬프트, 로그에 기록하지 않는다. 익명화하거나 합성 데이터를 쓴다. 권한 검증은 서버에서 하고 테스트는 다른 사용자·다른 테넌트의 접근 거절을 포함한다. 로그에는 추적 ID와 오류 분류를 남기되 비밀·민감 입력을 그대로 출력하지 않는다.

구체적 준비는 `templates/MIGRATION.md`를 사용한다.
