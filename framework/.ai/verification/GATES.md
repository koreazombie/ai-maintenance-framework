# 문서를 실행 검증으로 연결하기

이 파일은 연결 지침이며 실행되는 CI 설정이 아니다. 프로젝트의 실제 도구와 버전에 맞게 명령을 정하고 `.ai/PROJECT.md`에 기록한다.

| 규칙 | 실행 장치 | 중요한 한계 |
|---|---|---|
| 모듈 내부 의존 금지 | 언어/린터의 경로 규칙·의존 그래프 검사 | alias·재수출·동적 import·workspace 패키지도 검사해야 함 |
| 타 모듈 데이터 쓰기 금지 | 리포지토리 경계·코드 리뷰·가능한 DB 역할 분리 | 같은 DB 역할이면 문서와 import 검사만으로 SQL을 차단하지 못함 |
| 행동 계약 보존 | 공개 API 계약·소비자 테스트 | 타입 검사만으로 오류·부작용·동시성을 검증하지 못함 |
| 데이터 정합성 | DB 제약 + 실제 PostgreSQL 통합 검사 | mock DB에는 실제 잠금·격리 보장이 없음 |
| 권한 격리 | 다른 사용자/테넌트의 부정 시나리오 | UI 숨김은 서버 권한 검사가 아님 |
| 마이그레이션 호환 | 이전 스키마 fixture → 적용 → 구/신 코드 검증 | 빈 DB 생성 성공은 기존 데이터 검증이 아님 |
| 게이트 우회 방지 | CI 필수 체크와 보호된 병합 정책 | 설정과 권한이 실제 서비스에서 활성화돼야 함 |

## 최소 연결 순서

1. 이미 있는 명령과 테스트를 조사한다. 새 도구 도입 전에 기존 장치를 사용한다.
2. 타입/빌드/린트와 변경 대상의 행동 테스트를 실제로 실행한다.
3. 공개 진입점 규칙을 경계 검사에 등록한다. 정상 의존은 통과하고 내부 import 위반은 실패하는지 확인한다.
4. 데이터·동시성 작업은 격리된 실제 DB 검사 경로를 만든다.
5. CI에는 필수 검사를 연결하고 실패가 병합을 막는지 확인한다. 이 프레임워크만 복사해서 활성화됐다고 주장하지 않는다.

기존 위반이 많으면 기준선을 기록하고 신규 위반을 차단하는 방식으로 도입한다. 예외는 경로·사유·해소 조건을 갖고, 전체 규칙 비활성화로 처리하지 않는다.

REBUILD 검증은 구현 A/B 모두에 같은 계약 harness를 연결한다. 정답은 테스트 대상 코드의 helper로 계산하지 않는다. mutation testing이나 별도 리뷰는 중요 오류를 더 찾는 경우에 선택적으로 추가한다.
