# PATCH와 REBUILD

## 기본 판단

PATCH는 현재 구현의 일부를 고친다. REBUILD는 한 모듈의 내부 구현을 교체한다. 기본은 PATCH이며 코드가 보기 싫거나 새로 쓰는 편이 빠르다는 느낌만으로 REBUILD를 선택하지 않는다.

| 상황 | 판단 |
|---|---|
| 결함이 국소적이고 구조가 유지 가능 | PATCH |
| 계약·데이터 소유권이 불명확 | 먼저 조사·계약화, 국소 PATCH |
| 같은 이유의 수정이 반복되고 구조가 불변조건을 지키기 어려움 | REBUILD 후보, 준비 조건 확인 |
| 라이브러리/인프라 교체 | 어댑터 교체부터 검토 |
| 외부 계약·데이터 모델까지 바꿔야 함 | 별도 계약 변경·마이그레이션 작업; 내부 REBUILD로 숨기지 않음 |

후보 판단은 예상 영향 범위, 검증 비용, 복구 가능성, 운영 위험과 개선 효과를 비교한다. 수치 임계값을 근거 없이 만들지 않는다.

## REBUILD 준비 조건

1. 교체 경계·비범위·외부 소비자와 모든 부작용이 식별돼 있다.
2. 공개 행동 계약·불변조건·오류·권한·일관성·성능 기준이 확인돼 있다.
3. 기존 데이터와 구/신 구현을 검증할 대표 fixture·실행 가능한 검증 경로가 있다.
4. 교체 전 기준점과 정상 검증 결과가 있고 사용자 작업이 보존된다.
5. 코드 전환과 데이터·외부 부작용의 복구 방법이 각각 정의돼 있다.
6. 필요한 승인 범위와 실제 적용 환경이 확인돼 있다.

부족하면 바로 교체하지 않고 필요한 준비를 진행한다. 사용자가 REBUILD를 요청해도 이 준비를 생략하지 않는다.

## 실행 순서

기준점 보존 → 계약/검증 고정 → 내부 교체 → 같은 계약 검사 → 실제 인프라·데이터·소비자 호환성 확인 → 차이 검토 → 전환·관찰 → 안정화 후 구 구현 제거.

구현 교체와 계약·테스트 정답·스키마 변경을 한꺼번에 묶지 않는다. 불가피하게 함께 바뀌면 각 변경 이유와 이전/이후 검증을 구분한다.

shadow 실행은 읽기 또는 부작용이 격리된 경로에만 사용한다. 결제·메일·회원권 차감 같은 작업을 두 구현에서 실제로 두 번 실행하지 않는다. 전환 플래그는 선택 수단이며 작은 변경에 무조건 추가하지 않는다.

중단 조건은 계약 회귀, 데이터 불변조건 위반, 승인된 성능 기준 초과, 설명되지 않는 결과 차이다. 데이터가 변했다면 코드만 되돌린 뒤 정상이라고 선언하지 않는다. 결과는 `templates/CHANGE.md`에 남긴다.
