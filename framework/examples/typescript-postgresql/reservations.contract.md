# 예약 생성 계약 — 가상 예시

버전 1 · 상태: 예시/업무 확인 필요
소유자: reservations · 소비자: 예약 HTTP 어댑터·운영 관리 화면
공개 타입: [contracts.ts](contracts.ts)

## 가정과 비범위

한 DB의 트랜잭션으로 예약과 회원권 차감을 처리한다. 결제와 대기자 자동 배정은 이번 계약의 비범위다. 활성 예약의 동일 회원/수업 중복은 허용하지 않는다고 가정한다.

## 입력·출력

- 입력: tenantId, actorId, memberId, classId, membershipId, idempotencyKey.
- 출력: 예약 ID와 `confirmed` 상태. 같은 성공 요청의 재시도는 동일 예약을 반환한다.
- 이 예시는 string ID를 쓰지만 런타임 검증·인증이 필요하다. 클라이언트가 보내는 tenantId나 actorId를 신뢰하지 않고 인증 컨텍스트와 대조한다.

## 불변조건

- 권한 없는 사용자와 다른 테넌트는 예약·차감·이벤트를 만들 수 없다.
- 예약 완료는 좌석 확보·예약 저장·회원권 차감이 모두 성공한 상태다.
- 정원을 넘지 않고, 잔여 횟수가 음수가 되지 않으며 같은 예약에 대한 차감은 한 번이다.
- 어느 DB 단계가 실패해도 이 요청의 예약과 차감이 모두 남지 않는다.

## 오류·멱등성

오류는 VALIDATION_FAILED, FORBIDDEN, NO_CAPACITY, MEMBERSHIP_UNAVAILABLE, ALREADY_RESERVED, IDEMPOTENCY_CONFLICT, TEMPORARY_FAILURE로 분류한다. 공개 오류가 다른 테넌트의 자원 존재를 노출하지 않도록 한다.

멱등키 범위는 `(tenantId, createReservation, key)`다. 같은 키에 다른 정상화 입력을 넣으면 IDEMPOTENCY_CONFLICT이고 새 부작용은 없다. 동일 성공 요청은 다시 권한을 확인한 뒤 동일 예약을 반환한다. 실패한 요청은 확정된 성공 결과가 없으므로 재시도 시 다시 평가한다. TEMPORARY_FAILURE의 재시도에는 같은 키를 쓴다. 키/결과 보관 기간은 실제 프로젝트에서 결정해야 하며, 그 기간 이후의 중복 방지 기준도 명시해야 한다.

검증·권한 확인, 멱등키/요청 비교, 기존 활성 예약 중복, 좌석·회원권 판정의 순서와 정보 노출 정책은 구현 전에 확정한다. 좌석 부족과 회원권 불가가 동시에 발생할 때의 오류 우선순위는 아직 미확인이다. 소비자가 의존하면 계약을 먼저 보완한다.

## 트랜잭션·이벤트·성능

조립부가 시작한 단일 트랜잭션에 소유 모듈의 작업이 참여한다. 잠금/격리와 경쟁 처리는 실제 어댑터에서 결정하고 PostgreSQL 통합 검사로 확인한다. 이벤트가 필요하면 outbox 저장까지 동일 트랜잭션에 포함하며 이벤트 payload·버전·순서·소비자 멱등성 계약을 추가한다.

성능 임계값은 미설정. 기존 실측과 업무 요구를 바탕으로 정하고 REBUILD 전후 비교한다. 숫자를 임의로 확정하지 않는다.

## 검증과 호환성

[시나리오 문서](verification-scenarios.md)를 실제 테스트에 구현한다. API 형식 외에도 오류, 반복 호출, 권한, 원자성, 기존 데이터 호환성을 보존한다. 알려진 기존 버그는 계약 정답과 별도로 판정한다.
