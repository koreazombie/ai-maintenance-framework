# 독립 검증 시나리오 — 실행 테스트로 구현할 양식

아래는 실행 결과가 아니라 요구사항 기반 정답이다. Vitest/Jest/프로젝트의 기존 도구에 연결하고 실제 PostgreSQL에서 필요한 시나리오를 실행한다. fixture는 합성 데이터를 쓰고 다른 테스트와 DB 상태를 격리한다.

| ID | 준비/동작 | 기대 결과 | 검증 위치 |
|---|---|---|---|
| R01 | 좌석 1, 회원권 1, 권한 있음 → 예약 | confirmed, 예약 1개, 잔여 0, 차감 원장 1개 | 공개 유스케이스 + 실제 DB |
| R02 | 권한 없음/다른 tenant → 예약 | FORBIDDEN, 해당 요청의 예약·차감·이벤트 0 | 권한 통합 |
| R03 | 좌석 0, 회원권 유효 → 예약 | NO_CAPACITY, 해당 요청의 저장·차감 0 | 계약 + 실제 DB |
| R04 | 좌석 있음, 회원권 만료 → 예약 | MEMBERSHIP_UNAVAILABLE, 예약·차감 0 | 계약 + 실제 DB |
| R05 | 같은 성공 요청·같은 키 반복 | 동일 예약 ID, 예약·차감 각 1개 유지 | 멱등성 통합 |
| R06 | 같은 키·다른 유효 payload | IDEMPOTENCY_CONFLICT, 새 부작용 0 | 계약 + 실제 DB |
| R07 | 마지막 좌석에 서로 다른 두 회원이 동시 요청 | 성공 1, NO_CAPACITY 1, 정원 초과 없음 | 독립 DB 연결의 경쟁 검사 |
| R08 | 잔여 1회 회원권으로 서로 다른 두 수업 동시 요청 | 성공 1, 회원권 불가 1, 잔여 0 | 독립 DB 연결의 경쟁 검사 |
| R09 | 저장 도중 오류 주입 | TEMPORARY_FAILURE, 해당 예약·차감 모두 롤백 | 실제 DB 트랜잭션 |
| R10 | 같은 성공 요청을 동시에 제출 | 동일 ID, 예약·차감 각 1개 | 멱등키 경쟁 검사 |
| R11 | 같은 회원/수업, 서로 다른 키로 다시 요청 | ALREADY_RESERVED, 추가 차감 0 | 공개 계약 + UNIQUE 처리 |

최종 상태를 API 응답만으로 확인하지 않고 소유 모듈의 검증 경로나 테스트 전용 DB 조회로 확인한다. 테스트 DB 직접 조회는 제품 모듈의 교차 쓰기를 허용하는 예외가 아니다.

REBUILD 시 동일 harness를 구/신 구현에 연결하고 ID 생성·시각 등 계약상 허용 차이만 정규화한다. 오류·권한·횟수·정합성 차이를 정규화해서 숨기지 않는다. 알려진 기존 버그가 있다면 구 구현의 실패와 새 구현의 정답 통과를 함께 기록한다.

게이트 자체를 점검할 때는 별도 임시 분기/fixture에서 중복 차감 방지나 경계 규칙을 제거해 검사가 실패하는지 확인할 수 있다. 실제 제품의 제약을 제거한 상태로 병합하지 않는다.
