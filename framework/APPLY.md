# 프로젝트 적용 가이드

## 1. 병합할 범위

필수는 두 진입 파일과 `.ai/`다. `templates/`, `contracts/`, `verification/`는 작업에 사용할 양식과 검증 기준으로 함께 복사한다. 패키지의 `README.md`, `APPLY.md`, `PROMPTS.md`, `SOURCES.md`, `CHANGELOG.md`는 프로젝트 루트 문서를 대체하지 말고 필요하면 `docs/ai-framework/`에 보관한다. 이동한 안내 문서는 링크 경로를 조정한다. 예시는 참고용으로 두며 실제 제품 소스에 자동 복사하지 않는다.

숨김 폴더인 `.ai/`도 포함해 복사한다. 기존 `CLAUDE.md`, `AGENTS.md`, `.ai/`가 있으면 비교·병합한다. 백업 또는 버전 기준점을 남기고 사용자 파일을 덮어쓰지 않는다. 모노레포는 실제 프로젝트 루트와 하위 범위를 먼저 확인한다.

## 2. 설정과 첫 계약

`.ai/PROJECT.md`를 실제 설정으로 채운다. 템플릿은 `templates/PROJECT.md`를 이용한다. TypeScript/PostgreSQL이면 예시 설정의 항목을 참고하되 명령과 경로는 실제 프로젝트에서 확인한다.

첫 대상은 자주 변경되는 업무 모듈 하나가 좋다. 책임, 테이블 소유자, 공개 API, 소비자와 가장 중요한 불변조건부터 계약으로 정리한다. 계약 없는 기존 시스템은 소비 코드·테스트·스키마를 조사해 '확인됨/관찰됨/미확인'을 나눈다.

## 3. 도구가 지침을 읽는지 확인

Codex는 `AGENTS.md`를 지침으로 발견한다. 공통 Markdown 파일은 루트 진입점의 지시에 따라 직접 읽게 했다. `.ai/` 파일 전체가 자동 로드되는 것으로 취급하지 않는다. 상위/하위 지침과 `AGENTS.override.md`가 있는지도 확인한다. 자세한 발견 방식은 [공식 AGENTS.md 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)를 참고한다.

Claude Code 진입점은 공통 핵심 파일 세 개를 `@`로 가져온다. 작업별 상세 문서는 필요할 때 직접 읽게 한다. 자세한 가져오기 방식은 [공식 메모리 문서](https://code.claude.com/docs/en/memory)를 참고한다.

프로젝트 루트에서 각 도구의 새 세션을 열고 다음을 요청한다.

> 적용되는 지침 파일과 실제 읽은 공통 문서 경로를 알려 줘. 기본 변경 전략, 데이터 소유권 원칙, 미실행 검증 보고 규칙을 요약해 줘. 프로젝트 설정의 미확인 항목을 표시해 줘. 아직 코드는 수정하지 마.

응답을 파일 내용과 비교한다. 설명이 맞는 것만으로 지침의 모든 실행을 보장할 수는 없다. 이어서 작은 실제 변경으로 동작을 점검한다.

## 4. 한 모듈에서 시작

첫 변경에서는 PATCH를 적용하고 수용 시나리오와 필요한 검증을 확인한다. 공개 진입점, 데이터 쓰기 경계, 문서 업데이트와 최종 보고가 일치하는지 리뷰한다. 효과가 확인되면 인접 모듈에 확대한다. 기존 서비스를 한 번에 모범 구조로 다시 쓰지 않는다.

## 5. 강제 장치 연결

`verification/GATES.md`에 따라 기존 린터·테스트·CI·권한을 연결한다. 관련 테스트가 없으면 가장 중요한 불변조건부터 추가한다. 필수 검사가 실패했을 때 CI가 실제로 병합을 막는지 확인한다.

## 기존 프로젝트와 새 프로젝트

| 기존 프로젝트 | 새 프로젝트 |
|---|---|
| 현재 행동과 예외를 먼저 기록 | 업무 불변조건과 소유권을 먼저 설계 |
| 변경하는 경계부터 정리 | 최소 공개 계약과 수용 시나리오 작성 |
| 소비자 호환·데이터 보호 우선 | 모듈러 모놀리스에서 시작 |
| 기존 명령·구조를 유지하며 개선 | 실제 필요가 생기는 곳에 포트·어댑터 추가 |

## 선택 정책을 바꿀 때

기본 선택은 PATCH 우선/실용형이다. 적극적 재생성을 원하면 `.ai/CORE.md`와 `.ai/PROJECT.md`의 정책을 일치시킨다. 그래도 REBUILD 준비 조건과 데이터 보호는 유지한다. 엄격형을 도입하면 모든 변경 기록을 요구할 수 있지만 작은 작업의 비용도 비교한다.

## 유지관리

업무 규칙 변경 시 계약과 검증을 갱신하고, 명령·소유권·환경 변경 시 프로젝트 설정을 갱신한다. 반복되는 경계 위반과 재생성에서 실패한 시나리오를 바탕으로 규칙을 개선한다. 규칙을 늘리기 전에 기존 규칙의 모호함과 실행 장치 누락부터 해결한다.
